# 规则与来源升级接口

## 来源身份

未知文件首次使用前绑定稳定来源身份：

```http
POST /api/tasks/:taskId/sources/:artifactId/bind
Content-Type: application/json

{"system":"OA","reportType":"leave"}
```

字段映射仍由用户逐项确认。服务端以来源身份检索记忆，以结构指纹判断是否可复用；指纹不兼容的映射会返回但不会进入执行别名。

## 模型草案与本地编译

模型返回 `proposed / clarification_required / unsupported` 三态的非递归语义动作，只负责筛选、关联、白名单计算和模板列绑定。输入 artifact、工作表、列索引、规则版本、步骤 ID 和模板版本由服务端从 `basePlan` 确定性组装，再编译并校验为完整 `ProcessPlanV3`。模型不能直接提交文件路径、可执行表达式或运行结果。

V3 预演响应和正式运行审计清单都包含 `stages`。每个步骤记录 `inputRows / outputRows / isolatedRows`；关联、聚合、余额分配和拆分分别记录匹配数、分组数、分钟守恒和各分支行数，不使用单一全局行数等式替代专项对账。

## 规则生命周期

创建初始草稿：`POST /api/rules/:id/revisions`，请求体为 `{ "rule": ... }`。客户端传入的状态不会直接发布规则。

状态由服务端依次转换：

```text
POST /api/rules/:id/revisions/:version/validate
POST /api/rules/:id/revisions/:version/confirm
POST /api/rules/:id/revisions/:version/publish
POST /api/rules/:id/revisions/:version/supersede
```

发布请求必须显式提供 `sourceIdentity`。一次性规则在任务完整预演后确认到 `confirmed` 即可运行，不会自动进入长期规则库。

自然语言修改使用 `POST /api/rules/:id/revisions/propose-patch`。模型只能返回 `add_step / replace_step / remove_step` 增量操作和基础修订号；服务端应用后生成新草稿。恢复历史内容使用 `POST /api/rules/:id/restore`，同样生成新修订而非改写旧版本。

按步骤 ID 查看两个修订的新增、删除、修改和顺序变化：

```http
GET /api/rules/:id/diff?from=1&to=2
```

工作台已接入校验、确认、来源发布、自然语言增量修订、历史恢复和差异查看；所有操作仍调用相同服务端接口。

按来源检索当前已发布且已生效规则：

```http
GET /api/rules/resolve?sourceIdentity=oa:leave
```
