## 一、简要结论

系统已具备**本地文件级业务处理闭环**：上传和分析 ERP/OA/HR 表格，按已确认规则进行筛选、关联、计算、异常隔离和模板写出，并保留预演、确认、审计及运行历史。三类内置业务和受限通用规则引擎均可运行。其设计重点是让模型提出结构化规则，由本地 TypeScript 引擎验证和计算，避免模型直接生成业务数值。

当前适合作为**受控本地试运行版本**。不能认定为已满足需求单所要求的“目标 HR 系统直接导入成功”：真实 HR 环境导入、业务方独立逐单元格签认均未完成。网页对过期年假余额的确认还存在实际交互缺口，企业多人使用所需的访问控制也尚未具备。

## 二、架构与技术路线

```text
ERP / OA / HR 导出文件（.xls / .xlsx / .csv）
                ↓
Web 工作台 / CLI → Fastify 本地 API → 工作簿分析、来源身份和字段映射
                                      ↓
                自然语言 → 模型提出受限 RuleDraft / ProcessPlan
                                      ↓
                本地 Schema、字段、类型、依赖和条件覆盖校验
                                      ↓
                用户预演与确认 → 确定性 V3 引擎 → 模板写出与复读
                                      ↓
                目标文件、异常日志、阶段对账、审计清单与历史版本
```

- **入口层**：`apps/web` 是四段式工作台；`apps/cli` 支持文件检查、固定业务运行、V2 规则执行和异常日志操作；`apps/api` 承担任务、配置、模型建议、预演、确认和执行接口。
- **数据与规则层**：`packages/excel` 解析多工作表、保留源行与稳定列 ID，完成模板写出和复读；`packages/types` 用 Zod 定义计划、规则、模板和任务契约；`packages/core` 执行类型化 AST、跨表关联、聚合、筛选、顺序余额分配及拆分。
- **运行状态**：任务及映射记忆写入本地 SQLite，源文件和产物写入任务目录；规则与模板以版本化 JSON 保存在本地配置目录。执行前用文件哈希、计划/规则/模板绑定与确认状态防止旧确认复用；单机队列执行，支持幂等键、取消和中断恢复。
- **模型边界**：DeepSeek、硅基流动、Gemini、Qwen 与预留的 OpenAI 适配器共用接口。模型接收脱敏后的指令和表结构/统计画像，输出受限建议；本地校验和人工确认后才可执行。模型对任意新语句的正确理解不由现有测试保证。

## 三、技术栈与部署形态

| 层次 | 当前实现 |
| --- | --- |
| 运行与工程 | Node.js 24、pnpm 11、TypeScript 5、Monorepo |
| 前端 | React 19、Vite 7 |
| API / 存储 | Fastify 5、`node:sqlite`、本地文件目录；默认监听 `127.0.0.1:3210` |
| 表格 / 校验 | SheetJS 0.20.3、JSZip、Zod 4；支持 `.xls`、`.xlsx`、`.csv` 输入与模板化输出 |
| 测试 | Vitest、Playwright、ESLint、TypeScript 类型检查 |
| 模型 | 可配置的 HTTP provider；历史真实验收使用硅基流动托管的 `deepseek-ai/DeepSeek-V4-Flash` |

目前是**单机本地应用**：任务目录、SQLite 和规则配置都在本机；没有仓库内的多节点部署、身份系统或集中式权限管理方案。

## 四、用户使用简要说明

1. 使用 Node 24 和 pnpm 11，在仓库根目录执行 `pnpm install`，按需复制 `.env.example` 为 `.env` 并配置模型密钥，再执行 `pnpm dev`。网页默认地址为 `http://127.0.0.1:3211`。
2. 新建任务，上传系统导出的工作簿，点击“上传并分析”；核对工作表、表头、行数、来源身份与字段映射。通用来源需要绑定来源系统和报表类型。
3. 输入处理指令。内置业务可生成加班、请假或年假结算计划；通用任务可绑定已发布规则/模板，或提出一次性 V3 规则草案。模型不可用时，已确认的规则仍可执行。
4. 点击“完整预演”，检查行数、逐阶段对账、异常与输出样例。处理异常或修改来源、映射、规则后，重新预演和确认。
5. 确认计划后执行，下载 HR/目标文件、异常日志、审计清单和历史运行产物。年假结算需额外人工核实余额时点；当前网页在这一确认上有缺陷，详见 P0-1。

CLI 用法和参数见 [README](../README.md) 与 [运行手册](运行手册.md)。交付前应运行 `pnpm verify:artifacts`；真正的 HR 导入仍需在目标系统试导并记录结果。

## 七、问题清单与改进顺序

优先级按**业务结果风险、需求阻断程度、影响范围**排序。P0 为交付前必须解决或取得明确外部验收的事项；P1 为受控试运行向企业使用推进时优先处理；P2 为持续完善。

| 顺序 | 优先级 | 问题与证据 | 建议完成标准 |
| --- | --- | --- | --- |
| 1 | **P0** | **网页自动同意使用旧年假余额。** `apps/web/src/main.tsx` 的 `confirm()` 固定发送 `allowStaleBalance: true`，未向用户展示并单独确认余额时点；API 预演虽返回 `requiresStaleBalanceConfirmation`，其判断也未比较余额与请假日期，前端更未消费该标志。与[业务规则](业务规则.md)“旧余额必须显式确认”不符。 | 预演显示余额截至日与参与结算日期；仅在确属过期且用户明确勾选/签署后允许确认，并保存确认依据；增加拒绝和同意两条 E2E。 |
| 2 | **P0** | **目标 HR 导入和独立黄金结果签认缺失。** 需求单要求真实导入无格式错误及与人工公式结果完全一致；现有文件级替代验收与候选基线不足以证明这两点。 | 在真实 HR 测试环境记录导入接收/拒绝数和报错原文；由业务方独立核算并签认指定边界样本，固化新约束和回归。此项依赖外部环境/业务签认。 |
| 3 | **P1** | **没有用户身份与权限边界。** `apps/api/src/server.ts` 无鉴权，CORS 允许任意来源；任务列表、人员数据、下载、规则发布和删除接口均可直接调用。默认仅监听本机回环地址，若被代理或改为外部地址会扩大暴露。 | 接入身份认证和按任务/角色授权，约束 CORS 来源，记录真实操作人；对上传、下载和规则发布做权限回归。企业共享部署前完成。 |
| 4 | **P1** | **通用任务异常修正闭环不完整。** API 对 `task.generic` 直接拒绝源补丁，网页异常行也仅给固定业务任务显示修正/排除按钮。与需求单的人工复核及继续处理目标有落差。 | 通用 V2/V3 异常可按稳定 artifact/sheet/column/row ID 修正或排除，保存补丁、重新预演确认、保留运行历史；补充网页 E2E。 |
| 5 | **P1** | **规则配置仍偏工程化。** 映射、转换、关联、计算、筛选、模板六类规则没有完整逐字段表单；通用流程仍需手填规则/模板 ID 与受限 JSON。需求追踪矩阵 `CFG-02` 为“部分通过”。 | 六类常用配置均能在网页创建、校验、比较、发布和复用，JSON 保留为高级入口；用非开发人员完成三组新报表的配置验收。 |
| 6 | **P1** | **权威来源校验尚未闭环。** 规则文档指定员工身份以 HR Master Data 为准，但当前冲突处理主要是比较已有字段并隔离，未见 HR 主数据的时点化对接和人工核验记录。 | 明确 HR 主数据来源、有效期与工号复用规则；对身份冲突提供可追踪的人工裁决记录，裁决后重跑仍保留原始证据。 |
| 7 | **P2** | **泛化验收覆盖有限。** 三个新场景仅库存有网页 E2E，真实模型报告是五类固定表达测试；连续对话改规则、来源规则复用及异常注入矩阵仍待扩展。 | 为另两组新场景补完整网页路径、独立黄金样本和故障注入；新增连续对话与模型误解用例，定期复测。 |
| 8 | **P2** | **表头识别和单机吞吐有边界。** 自动表头检测只看前 20 行且采用启发式评分；API 将上传读入内存，执行为单机串行队列。复杂前言、超大文件或多用户并发需专项容量验证。 | 增加显式表头选择/预览纠错、文件体积与耗时基准、队列/内存监控和过载提示；依据实际数据规模定容量。 |
| 9 | **P2** | **文档存在时效差异。** 部分早期 M3/M4 文档仍保留“未真实联调”“尚无提交”等旧描述，与后来进度及当前提交不一致。 | 统一以版本和日期标注证据，更新运行手册及验收索引，避免将历史断点误作当前状态。 |

## 八、建议的下一阶段验收门槛

先修复旧余额确认并取得真实 HR 导入及业务黄金结果签认；随后补身份权限、通用异常修正和可视化规则编辑。验收时继续保留当前 Node 24 全门禁，并将真实导入记录、人工签认、输入/输出哈希与规则版本绑定到同一任务审计清单。达到这些条件后，才适合从“受控本地试运行”提升为面向企业用户的正式交付结论。
